# REST API Specification v1.0

## 1. Rules

Base path:

``` text
/api
```

JSON request/response.

Authentication is required for all endpoints except login and the device
bootstrap endpoints below. Device bootstrap endpoints authenticate with a
per-device secret generated by the ESP. They do not expose user Homes.

Frontend must use these contracts and must not access PostgreSQL
directly.

### DELETE /api/homes/:homeId

Deletes the owned Home and all of its Rooms, Devices, device data, OTA jobs,
Automation Rules, and Automation Logs. The client must obtain explicit user
confirmation before calling this endpoint.

Response: `204 No Content`.

## 5. Devices

### GET /api/rooms/:roomId/devices

Response:

``` json
[
  {
    "id": "uuid",
    "deviceId": "esp32-c3-001",
    "name": "ESP32 phòng khách",
    "status": "online",
    "firmwareVersion": "1.0.0",
    "lastSeenAt": "2026-10-05T08:00:00Z",
    "capabilities": []
  }
]
```

### POST /api/rooms/:roomId/devices

Provisions an ESP32 identity in a Room before it starts sending MQTT messages.

Request:

``` json
{
  "deviceId": "esp32-c3-001",
  "name": "ESP32 phòng khách"
}
```

Response: the created Device with initial `status` of `unknown`.

`deviceId` must be unique. The Device becomes `online` only after an MQTT
availability message is received.

### GET /api/devices/:deviceId

Returns complete device detail.

### PUT /api/devices/:deviceId

Editable fields may include:

``` json
{
  "name": "ESP32 phòng khách"
}
```

### DELETE /api/devices/:deviceId

Authenticated Home owner removes the Device, pairing, telemetry, state/history,
commands, configuration and OTA jobs. Response `204 No Content`. The Dashboard
must confirm this destructive action. A connected ESP detects that its
bootstrap secret is revoked, clears its pairing locally and opens SoftAP for a
new pairing; Wi-Fi credentials and hardware GPIO settings remain stored.

## 9. Commands

### POST /api/devices/:deviceId/commands

Request:

``` json
{
  "commandType": "set_relay",
  "payload": {
    "capability": "relay_1",
    "state": true
  }
}
```

Response immediately after command creation:

``` json
{
  "commandId": "cmd-uuid",
  "status": "PENDING"
}
```

Backend then checks availability, publishes MQTT, waits for State, and
updates command status.

### GET /api/commands/:commandId

Response:

``` json
{
  "commandId": "cmd-uuid",
  "status": "SUCCESS",
  "retryCount": 0,
  "completedAt": "2026-10-05T08:00:05Z"
}
```

## 10. Configuration

### GET /api/devices/:deviceId/configuration

### PUT /api/devices/:deviceId/configuration

Request example:

``` json
{
  "telemetry_interval": 30,
  "relay_1_name": "Đèn phòng khách",
  "relay_metadata": {
    "relay_1": {
      "name": "Đèn phòng khách",
      "kind": "light",
      "description": "Đèn trần khu vực sofa"
    }
  }
}
```

Backend increments `config_version` and publishes configuration through
MQTT.

The request may also contain the `hardware` object defined in MQTT_SPEC §11.
Hardware pin changes require the device to be online; ESP validates them and
restarts after accepting the configuration. Query configuration status to
observe `applied_config`.

`relay_metadata` gives each logical relay a user-facing identity. Supported
`kind` values are `light`, `pump`, `fan`, `socket`, `curtain`, and `other`.
It is stored in `device_capabilities.config`; `relay_N` remains the immutable
MQTT instance code used for commands.

### GET /api/devices/:deviceId/configuration/status

Returns desired and applied configuration.

## 13. Voice AI

### POST /api/voice/command

Input after Speech-to-Text:

``` json
{
  "text": "Bật đèn phòng khách"
}
```

Expected internal result:

``` json
{
  "intent": "CONTROL_DEVICE",
  "parameters": {
    "target": "đèn phòng khách",
    "state": true
  }
}
```

Backend resolves target, validates Home authorization, executes normal
command flow, and returns:

``` json
{
  "success": true,
  "message": "Đã bật đèn phòng khách.",
  "commandId": "uuid"
}
```

AI must not publish MQTT directly.

## 13a. Device pairing and bootstrap

`POST /api/provisioning/register` (device secret): `{ "deviceId": "esp32-c3-aabbccdd", "pairingCode": "A1B2C3D4E5", "deviceSecret": "32 random hex bytes" }`. Creates a pending pairing that expires in 15 minutes. Re-registration of an existing pending pairing requires its secret. Response `{ "status": "pending", "expiresAt": "ISO_DATE" }`.

`POST /api/provisioning/bootstrap` (device secret): `{ "deviceId": "...", "deviceSecret": "..." }`. Pending response `{ "status": "pending" }`. Paired response `{ "status": "paired", "deviceId": "...", "homeId": "uuid", "roomId": "uuid", "mqtt": { "uri": "mqtt://broker:1883", "username": "", "password": "" } }`. Firmware polls this endpoint to recover broker changes. No caching.

`POST /api/devices/pair` (user session): `{ "pairingCode": "A1B2C3D4E5", "name": "Đèn phòng khách", "homeId": "uuid", "roomId": "uuid", "mqttUri": "mqtt://broker:1883" }`. Requires ownership of Home and membership of Room; consumes code once, creates Device with status `unknown`, returns Device. `404` for unknown/expired code, `409` if already paired/device ID exists.

`PUT /api/devices/:deviceId/broker` (user session): `{ "mqttUri": "mqtt://new-broker:1883" }`. Updates bootstrap configuration for an owned, paired Device. ESP learns the new address through REST polling while Wi-Fi is connected.

## 14. HTTP errors

Use: - `400` invalid input - `401` unauthenticated - `403` Home
authorization failure - `404` resource not found - `409` conflict -
`422` validation error - `500` unexpected server error - `503` dependent
service unavailable
